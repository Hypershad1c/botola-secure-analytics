## Phase 1 Execution Plan: Foundation, Database, Ingestion Skeleton, and Security Baseline

**Version:** 1.0  
**Status:** Proposed implementation baseline  
**Repository:** `Hypershad1c/botola-secure-analytics`  
**Primary deployment target:** Vercel for the web application and serverless request handlers  
**Author:** Manus AI

## 1. Purpose and Phase Boundary

Phase 1 establishes the production foundation for Botola Secure Analytics v2. It does not attempt to build the complete football intelligence product, live match center, machine-learning system, AI analyst, or cybersecurity operations center. Instead, it creates the stable contracts on which those capabilities can be added without replacing the application architecture.

The phase must deliver a runnable Next.js and TypeScript application, a PostgreSQL database managed through Prisma, a versioned initial schema and migration, seed infrastructure, an ingestion-job contract, a raw-data retention strategy, the first source adapter boundary, authentication and authorization foundations, structured logging, error handling, CI checks, and tests for entity normalization and import validation. The first historical Botola Pro season should be imported only after the schema and pipeline contracts are in place.

> **Phase 1 principle:** The web application is a request-serving system. Ingestion, bulk parsing, feature generation, simulations, and model training are background workloads and must not be hidden inside ordinary web requests.

The current GitHub repository is effectively empty apart from a README, so Phase 1 may establish the project structure cleanly rather than preserving an existing application architecture.

## 2. Architecture Decisions

### 2.1 Target architecture

The system is divided into four deployable concerns:

| Concern | Responsibility | Initial location |
|---|---|---|
| Web application | User interface, authenticated application routes, read APIs, admin operations, health checks | Next.js application deployed to Vercel |
| Database | Canonical football data, provenance, identities, security records, ingestion metadata | Managed PostgreSQL |
| Background ingestion | Downloading, parsing, normalizing, validating, deduplicating, and importing external datasets | Separate worker or scheduled execution environment; never a long-running Vercel request |
| Object storage | Immutable raw CSV artifacts and import reports | S3-compatible object storage; PostgreSQL stores metadata and checksums |

Vercel Functions are suitable for bounded request handlers, but they have execution, payload, memory, and bundle limits. The current Vercel documentation lists a maximum request/response payload of 4.5 MB and finite function durations, so a CSV importer must not upload or parse an entire season through a user-facing request.[3] The application should instead create an ingestion run, place the work on a background execution path, and let the web layer display status.

The initial background execution choice should remain provider-neutral. Implement the worker as a normal TypeScript module with a command-line entry point and an explicit `IngestionJob` interface. This permits a first local run, a CI/manual run, a scheduled worker, or a later queue-backed deployment without changing parsing and domain logic.

### 2.2 Database and migration policy

PostgreSQL is the system of record. Prisma is the schema contract, type generator, and migration mechanism. Migration files are committed to Git, reviewed as code, and applied to staging and production with a deployment-only command. Prisma's migration documentation emphasizes that migrations are versioned, reviewable changes that move the actual database toward the schema contract.[1]

The project must pin a Prisma major version rather than floating on `latest`. The exact CLI commands should be verified against the pinned version during bootstrap because Prisma's migration workflow evolves. The invariant is that schema changes happen through reviewed migrations, never through ad-hoc production edits.

### 2.3 Identifier and timestamp policy

All domain identifiers use UUIDs generated by PostgreSQL through Prisma defaults. External provider identifiers are stored separately and are never used as primary keys. All persisted timestamps are UTC `timestamptz(3)` values. A source's original date/time and timezone may be retained in raw payload metadata, but canonical timestamps are normalized to UTC.

### 2.4 Raw, normalized, and canonical data

The ingestion pipeline has three durable representations:

1. **Raw artifact:** the original downloaded file or API response, stored immutably in object storage and referenced by checksum.
2. **Staged record:** parsed values and source-specific fields stored in a normalized JSON envelope for validation and conflict review.
3. **Canonical record:** validated entities and relationships represented by relational tables and used by application features.

No source adapter may write directly to canonical tables. Every import creates an `IngestionRun`, records the source and artifact, parses into staged records, validates them, resolves aliases, records conflicts, and only then commits accepted canonical changes.

### 2.5 Source precedence

The source priority is configuration, not hard-coded business logic:

| Priority | Source | Initial role |
|---:|---|---|
| 10 | FootyStats historical datasets | Primary historical Botola Pro import source |
| 20 | FootyStats API | Programmatic enrichment where permitted |
| 30 | API-Football | Secondary verification and future live/upcoming data |
| 40 | Manual admin correction | Explicit, auditable override; never silent |

The source priority is not a claim about data quality or licensing. Before production ingestion, the project owner must confirm permission to download, store, enrich, and redistribute each dataset. A source conflict is retained in `DataConflict`; it is not silently overwritten.

### 2.6 Authentication strategy

Phase 1 should implement an authentication adapter rather than entangling football features with a provider-specific login implementation. The adapter exposes `getCurrentUser`, `requireUser`, `requirePermission`, and session-revocation functions. If a managed OAuth provider is selected, the provider identity is stored in `UserIdentity`; if local credentials are required, password hashes are stored in a separate credential model.

Passwords must never be stored in plaintext. OWASP recommends modern adaptive password hashing such as Argon2id and specifies a minimum Argon2id configuration based on memory, iterations, and parallelism.[4] Phase 1 should use an audited Argon2id library with parameters benchmarked in the deployment environment, while keeping the hash string self-describing so work factors can be upgraded later.

### 3.1 Directory ownership rules

| Directory | Rule |
|---|---|
| `app/` | Transport and page composition only. Route handlers validate input and delegate to services. |
| `features/` | User-facing feature modules and feature-specific server orchestration. |
| `services/` | Business workflows and use cases. Services may call repositories, but not React code. |
| `repositories/` | Database access and persistence queries. Repositories do not decide authorization policy. |
| `src/domain/` | Pure domain types and deterministic rules that can be tested without a database. |
| `prisma/` | Database contract, migrations, and deterministic development seed. |
| `scripts/` | Explicit local or worker commands; scripts must be safe to run repeatedly. |
| `docs/adr/` | Architectural decisions, including the reason for any later deviation. |
| `tests/` | Unit, integration, and contract tests with fixtures. |

The existing repository has only a minimal README, so the first commit may create this structure in one bootstrap change. Subsequent commits should be narrow and organized by deliverable rather than by UI page.

### 4.1 Schema validation before migration generation

Before committing the migration, run `prisma format`, `prisma validate`, and a clean database migration in CI. The schema is a design baseline and must be compiled and validated rather than copied blindly.

### 4.2 Schema implementation notes

The `EntityAlias` model uses nullable foreign keys because a source alias maps to exactly one canonical entity type. Add a database-level check constraint in a follow-up SQL migration or Prisma-supported extension to ensure exactly one target foreign key is populated for each alias. If the pinned Prisma version cannot express that constraint declaratively, include it in the reviewed SQL migration and document it in the ADR.

The `Match` uniqueness rule is intentionally conservative because a source may omit kickoff time. If `kickoffAt` is null, PostgreSQL permits multiple rows under a conventional unique constraint. The ingestion deduplicator must therefore compute a deterministic match fingerprint from competition, season, normalized home team, normalized away team, date bucket, and source identifiers before canonical insertion.

The initial schema stores `sourceRecords` and `rawStats` as JSON for provenance and fields not yet modeled. This is not a license to treat JSON as the primary analytics model. Any field used for filtering, joining, ranking, or metric computation must be promoted to a typed column in a later reviewed migration.

## 6. Ingestion Architecture for Phase 1

### 6.1 Pipeline contract

The ingestion service must implement the following stages:

```text
SourceAdapter
  → RawArtifactStore
  → Parser
  → StagingWriter
  → Normalizer
  → Validator
  → Deduplicator
  → ConflictResolver
  → CanonicalImporter
  → IngestionReport
```

Each stage accepts a typed input and returns a typed output. It must be possible to run parser, normalizer, validator, and deduplicator tests without a database or network connection.

```ts
export type SourceRecord = {
  sourceCode: string;
  datasetName: string;
  datasetVersion?: string;
  sourceRecordId?: string;
  rowNumber?: number;
  payload: Record<string, unknown>;
};

export type NormalizedRecord = SourceRecord & {
  entityType: "competition" | "season" | "team" | "player" | "match" | "standing";
  normalized: Record<string, unknown>;
  warnings: string[];
};

export type ValidationResult = {
  status: "accepted" | "rejected" | "duplicate" | "conflict";
  errors: Array<{ code: string; field?: string; message: string }>;
  warnings: string[];
};
```

### 6.2 Source adapter boundary

The FootyStats adapter should not know Prisma models. It should know how to retrieve and parse the source's CSV files into `SourceRecord` values. The adapter must support a local fixture path so development and CI do not depend on a live website.

The first import should use one historical Botola Pro season selected after confirming that the source file is available and legally usable. If 2025/26 is incomplete or unavailable, use the latest complete season and record the choice in the ingestion report. The import must not fabricate missing player or match data.

### 6.3 Normalization rules

At minimum, normalization must:

| Field | Rule |
|---|---|
| Team names | Unicode normalize, trim, collapse whitespace, lowercase comparison key, preserve display form, resolve aliases such as Raja CA and Raja Casablanca |
| Player names | Normalize punctuation and whitespace, preserve original name, use source identity when available, do not merge ambiguous names automatically |
| Competition | Map source labels to canonical competition and competition type |
| Season | Convert source labels into a canonical season name such as `2024/25` and associate it with one competition |
| Dates | Parse source date formats, reject impossible dates, store UTC canonical timestamp where time is known |
| Scores | Accept non-negative integer scores only; preserve null when genuinely unavailable |
| Positions | Map source labels to the controlled enum and use `UNKNOWN` when not safely classifiable |
| Countries | Normalize to ISO alpha-2 where possible, otherwise preserve source value in provenance metadata |

Ambiguous entity matches must become `DataConflict` records or rejected records. The normalizer must never silently merge two players because their display names are similar.

### 6.4 Validation rules

The Phase 1 validator must check:

1. Required source fields exist.
2. Team and player names are non-empty after normalization.
3. Scores are non-negative integers.
4. Match dates are valid and fall within a plausible season window.
5. Home and away teams are distinct.
6. A match belongs to the selected competition and season.
7. Duplicate source records are detected by source ID, file row fingerprint, and entity-specific fingerprints.
8. Match events refer to the correct match and use valid minute values.
9. Standings have non-negative played, win, draw, and loss counts.
10. Team points and goal difference are internally consistent when the source provides a complete table.
11. Player/team relationships are not created from an unresolved ambiguous alias.
12. All rejected records include a machine-readable error code and human-readable message.

### 6.5 Transaction boundary

Each logical canonical entity group should be imported in a transaction, but the entire season should not require one unbounded database transaction. A recommended order is:

```text
competition and season
  → teams, players, venues, referees
  → matches
  → events, lineups, stats, standings
```

The import is restartable. Each stage records progress in `IngestionRun` and `StagedRecord`. Re-running the same raw artifact must not create duplicate canonical entities. A failed run remains inspectable and may be resumed or explicitly cancelled.

### 6.6 Ingestion report

Every run must produce a JSON report and a human-readable Markdown report containing:

```text
Run ID
Source and artifact checksum
Dataset and season
Started and completed timestamps
Records seen
Records parsed
Records accepted
Duplicates
Rejected records
Conflicts
Canonical entities created
Canonical entities updated
Validation error counts by code
Warnings
Next action
```

The report is stored in object storage, while the summary counts and storage key are stored on `IngestionRun`. Example values in documentation must be clearly marked as examples; the application must not display made-up counts as real data.

## 7. Security Foundation

### 7.1 Authentication and sessions

Phase 1 must establish:

| Control | Implementation requirement |
|---|---|
| Password storage | Argon2id through a maintained library; benchmark parameters and store a self-describing hash |
| Session cookies | `HttpOnly`, `Secure` in production, explicit `SameSite`, narrow path, short-lived access session, revocation support |
| Session persistence | Store only token hashes, not bearer tokens, in PostgreSQL |
| Session rotation | Rotate refresh tokens when refresh-token sessions are used; revoke the previous token family on reuse |
| MFA boundary | Define a TOTP provider interface even if the full UI is deferred to the security phase |
| Account status | Enforce `ACTIVE` before issuing an authenticated session |
| Password reset | Single-use, expiring, hashed reset tokens; always audit requests and completion |
| Login errors | Do not reveal whether an email exists; rate-limit by account and source signals |

### 7.2 Authorization

Authorization must be permission-based, not scattered role-name comparisons. Add a server-side guard with this conceptual interface:

```ts
requirePermission(ctx, "football.import");
requirePermission(ctx, "security.read");
requirePermission(ctx, "admin.manage_users");
```

The initial roles are bundles of permissions. A user may have more than one role. Deny by default. Authorization checks must execute on the server for every protected operation; hiding a navigation item is not an authorization control.

### 7.3 Security events and audit events

Security events describe authentication, abuse, and suspicious activity. Audit logs describe a user or system actor changing a resource. Both must include a correlation/request ID where available. IP addresses and user agents should be hashed or minimized for analytics unless a documented incident-response requirement justifies retaining the raw value.

Do not log passwords, access tokens, refresh tokens, session cookies, API keys, or full authorization headers. Redaction must happen in the logger before a record reaches stdout, an external sink, or PostgreSQL.

### 7.4 HTTP and application controls

The initial application must configure:

- Strict input validation at route and service boundaries using Zod or an equivalent schema library.
- Secure response headers, including a documented Content Security Policy suitable for the selected authentication and asset configuration.
- CSRF protection for cookie-authenticated state-changing requests where the framework does not already provide an equivalent defense.
- Rate limiting for login, password reset, administrative mutations, and ingestion-trigger operations.
- Safe error responses that expose a request ID but not stack traces or provider secrets.
- Dependency auditing and lockfile review in CI.
- No secrets in source, fixtures, logs, client bundles, or Git history.

OWASP's password-storage guidance should be treated as the minimum password baseline, not the complete application security standard.[4]

|---|---|

### 10.1 Minimum fixtures

- A valid season with at least two teams and multiple matches.
- Equivalent team aliases such as `Raja CA`, `Raja Casablanca`, and `Raja Club Athletic`.
- A duplicate match row.
- A conflicting score row.
- An invalid negative score.
- An impossible date.
- A missing team name.
- An ambiguous player name that must not be auto-merged.
- A match with missing optional statistics that must remain null rather than zero.

The migration job must use a clean disposable PostgreSQL instance and must test both applying migrations and running the seed. CI must not call live football providers.

Implement the authentication adapter, session persistence, permission guard, audit logger, security-event logger, redaction rules, and protected health/readiness behavior. Defer polished login UI if necessary, but do not defer server-side authorization boundaries.

**Deliverables:** auth service contract, RBAC checks, secure session record handling, audit/security tests.

### Step 6 — Ingestion contracts and fixture pipeline

Implement the source adapter interface, raw-artifact metadata interface, staging record writer, normalization library, validation library, deduplicator, conflict writer, and report generator. Start with local fixture input and no external network dependency.

**Deliverables:** import command, fixture importer, deterministic report, unit and integration tests.

### Step 7 — FootyStats adapter and one-season test import

After confirming source access and permitted use, implement the CSV adapter for the selected complete Botola Pro season. Store the downloaded artifact with a checksum. Run the full pipeline, review rejected and conflicting rows, and resolve only through explicit rules or auditable manual mappings.

**Deliverables:** source adapter, raw artifact record, canonical season import, ingestion report, conflict list, operator runbook.

### Step 8 — CI, build, and deployment readiness

Complete CI gates, production build, migration verification, environment validation, security checks, and Vercel configuration. Verify that the web app serves health and readiness endpoints and that the worker command can run without importing web UI modules.

**Deliverables:** green CI, deployable web application, migration runbook, worker runbook, known-issues register.

## 12. Phase 1 Acceptance Criteria

Phase 1 is accepted only when all of the following are true:

| ID | Acceptance criterion | Evidence |
|---|---|---|
| P1-01 | A clean checkout installs and starts locally using documented commands. | README walkthrough and CI log |
| P1-02 | PostgreSQL migrations apply successfully to an empty database. | Migration CI job |
| P1-03 | Prisma schema validation, client generation, formatting, and type checking pass. | CI artifacts |
| P1-04 | Seed data is idempotent and creates roles, permissions, and source definitions without secrets. | Seed integration test |
| P1-05 | The web layer has liveness and readiness endpoints with safe failure behavior. | Route tests |
| P1-06 | Protected operations enforce permission checks server-side and default to deny. | Authorization tests |
| P1-07 | Authentication and administrative actions emit security and audit events without sensitive-token leakage. | Redaction and event tests |
| P1-08 | The ingestion pipeline can process local fixtures through parsing, normalization, validation, deduplication, staging, canonical persistence, and reporting. | Integration test and report artifact |
| P1-09 | Team aliases resolve to one canonical team, while ambiguous player aliases are not silently merged. | Normalization tests and conflict record |
| P1-10 | Re-running the same artifact is idempotent. | Regression test with unchanged canonical counts |
| P1-11 | One permitted historical Botola Pro season is imported, and the report contains real counts, errors, duplicates, and conflicts. | Committed or externally stored report reference |
| P1-12 | All rejected records are explainable by machine-readable validation codes. | Error summary and fixture assertions |
| P1-13 | The Vercel application does not require a permanently running Node.js server or long-running import request. | Deployment configuration and architecture ADR |
| P1-14 | CI validates migrations and does not depend on live source websites or APIs. | CI configuration |
| P1-15 | The repository contains architecture, local setup, security, ingestion, and migration runbooks. | `docs/` review |

The phase should not be marked complete merely because a dashboard page renders. The import report, migration evidence, and test evidence are the primary completion artifacts.

## 14. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Source data is unavailable or restricted | Import cannot be legally or technically completed | Confirm access and licensing first; keep adapter fixture-driven and source-neutral |
| Source schemas change | Import breaks or silently mis-maps fields | Store artifact checksum and parser version; fail on unknown required columns; retain raw data |
| Duplicate or ambiguous entities | Incorrect analytics and relationships | Alias tables, deterministic fingerprints, conflict records, no fuzzy auto-merge without thresholds and review |
| Serverless connection exhaustion | Intermittent production database failures | Use a pooled connection strategy, cached client, bounded queries, and readiness checks |
| Long-running import in request path | Timeouts and partial writes | Worker command and resumable ingestion run; request only creates or inspects a run |
| Overly broad permissions | Data or security compromise | Permission-based guards, default deny, audit all administrative changes |
| Sensitive logs | Credential leakage | Central redaction, denylist tests, token hashing, no raw authorization headers |
| Premature analytics schema | Costly rewrites and incorrect metrics | Defer derived metrics until a metric dictionary and methodology are approved |
| Migration drift | Staging and production divergence | Migration-only production changes, CI against clean PostgreSQL, review generated SQL |

## 15. Decisions Required Before Coding Starts

The following decisions are architecture-relevant and should be recorded before implementation begins:

1. Which managed PostgreSQL provider and connection-pooling mode will be used in staging and production?
2. Which object-storage provider will hold immutable raw artifacts and reports?
3. Which authentication provider is the default, and is local password authentication required in Phase 1?
4. Which complete Botola Pro season is the first legally usable import target?
5. Is Redis required in Phase 1 for rate limiting, or should the first implementation use a provider-managed rate limiter?
6. Where will the worker execute for scheduled and manual ingestion runs?
7. What retention period applies to raw source files, staged records, security events, and audit logs?
8. Who may resolve data conflicts, and what evidence is required for a manual correction?

If these questions are not answered, implementation may proceed with local-development defaults and explicit placeholders, but production deployment must remain blocked until the decisions are recorded.

---

## 16. Definition of Done

Phase 1 is done when a new developer can clone the repository, configure local environment values, start PostgreSQL, apply migrations, seed the database, run the test suite, execute the fixture importer, inspect an ingestion report, and understand the architecture from the repository documentation. A reviewer must be able to trace every imported canonical value to a source artifact or an explicit manual resolution, and every protected operation to a server-side permission check.

The next phase may then add broader football coverage and analytics calculations. It must not bypass the Phase 1 provenance, validation, migration, and security contracts.
